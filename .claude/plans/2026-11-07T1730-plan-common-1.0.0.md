# common 1.0.0: stack-agnostic secrets CLI, Terraform module, Make contract and naming

## Why

The owner wants one way to handle secrets and one set of entry points in every repository, whatever the stack: Rust, Next.js, Python, Kotlin or Scala. Putting the secrets CLI inside the FastAPI blueprint would tie it to Python and duplicate it for Next.js. So a top-level, stack-agnostic part of this repository carries:

- the secrets CLI;
- the Terraform module that creates the secret containers and their access;
- the Make contract;
- the naming conventions.

Each blueprint (Next.js, FastAPI, later others) vendors it. GCP is the first and only backend in 1.0.0, because the owner runs apps mostly on GCP.

## Name and place

`common/` at the repository root, next to `nextjs/` and `fastapi/`.

- **Why not `shared/`:** both templates already have a `src/shared/` folder, and a second "shared" at the root would be ambiguous in docs and in grep.
- **Why not `tools/`:** that names the form rather than the scope, and the declaration and naming rules are not tools.
- **How `common/` differs from a blueprint:** it has no template and no architecture. Its own `README.md` and `CHANGELOG.md` say so.

The root README changes:

- **Blueprint table:** gains a "Shared parts" row for `common/`.
- **Convention line:** "Nothing here is specific to a company, product or cloud account" becomes "...to a company, product, or cloud account or project. `common/` targets GCP in 1.0.0 behind a backend seam, with no account, project or organisation ids."

**Repository conventions observed and kept:**

- Commits are Conventional Commits, with the top folder as scope (`feat(nextjs): ...`, `docs(plans): ...`), so `common/` uses `feat(common): ...`.
- Branches are `feat/<area>-<version>`, so this one is `feat/common-1.0.0`.

## Scope

### A. Principle: the best secret is none

Before anything is stored, remove the need for it. Every item below is keyless on GCP:

- **Service identities** for every runtime (web, worker, migrate, extra services). Google APIs are reached through the attached identity and Application Default Credentials, never a key file.
- **CI through Workload Identity Federation** (`google-github-actions/auth@v3`, `id-token: write`): no service-account keys in CI.
- **The database through Cloud SQL IAM authentication.** A connector authenticates the runtime identity with a short-lived OAuth token, so there is no database password. The Cloud SQL docs list the Auth Proxy and the Go, Java and Python connectors. The Python connector supports `psycopg` with `enable_iam_auth=True`. The instance needs the `cloudsql.iam_authentication` flag, and IAM login works over TLS only.
- **What remains:** third-party API keys and webhook signing secrets. The CLI and the Terraform module exist only for these.

### B. Naming conventions

**One rule for every cloud resource: `<repo>-<kind>-<env>`.** The environment is always in the name, even though each environment also gets its own GCP project (Google's best practice separates environments into projects). Explicit names survive cross-project IAM grants, logs, billing exports and copy-paste mistakes.

**`<repo>`:** the repository name in lowercase, with `_` and `.` turned into `-`, 3 to 11 characters.

- The limit comes from service accounts, whose ID must be 6 to 30 characters of lowercase letters, digits and dashes (IAM docs). The longest identity name is a 10-character kind plus `staging` plus 2 dashes, which leaves 11 characters for the repo.
- A longer repository name gets a fixed short form, declared once in the manifest as `repo`, and used everywhere: never only where a name overflows.
- Example: `shop-platform-backend` becomes `shop-backend`, still too long, so it becomes `shop`.

**`<env>`:** `dev`, `staging` or `prod`, the only allowed spellings, plus `pr-<n>` (n up to 4 digits) for previews.

**`<kind>`:** from this vocabulary. Kinds that name a service account are at most 10 characters.

| Kind | Names | Example (`shop`, `prod`) |
| --- | --- | --- |
| `web` | Cloud Run web service and its service account | `shop-web-prod` |
| `worker` | Cloud Run worker (service or worker pool) and its service account | `shop-worker-prod` |
| `migrate` | Cloud Run migration job and its service account | `shop-migrate-prod` |
| `<service>` | an extra runtime under `services/<name>/`: Cloud Run service and its service account | `shop-transcribe-prod` |
| `ci` | CI identity: build, push images, read secret metadata | `shop-ci-prod` |
| `deploy` | deploy identity: new revisions, run the migrate job; no secret access | `shop-deploy-prod` |
| `images` | Artifact Registry repository | `shop-images-prod` |
| `files` | Cloud Storage bucket for app files | `shop-files-prod` |
| `tfstate` | Cloud Storage bucket for Terraform state | `shop-tfstate-prod` |
| `sql` | Cloud SQL instance | `shop-sql-prod` |
| `db` | Postgres database, with underscores: `<repo>_<env>` | `shop_prod` |
| `secrets-rotation` | Pub/Sub topic for rotation notices | `shop-secrets-rotation-prod` |

Why `db` uses underscores: unquoted Postgres identifiers allow letters, digits, `_` and `$` but not `-`. A hyphenated name must be quoted everywhere it appears. The maximum is 63 bytes (PostgreSQL lexical structure docs).

**Secrets: `<repo>-<purpose>-<env>`**, for example `shop-payments-api-key-prod`.

- `<purpose>` is lowercase kebab-case, names the vendor and the use, and never repeats the repo or the environment.
- Secret Manager allows letters, digits, `-` and `_`, up to 255 characters.
- **Environment variable:** `<purpose>` in UPPER_SNAKE (`-` becomes `_`), so `PAYMENTS_API_KEY`. The environment is not in the variable name, because each environment injects its own value. A mounted secret file uses the same name as the variable.

**Settings field per stack.** One config module per app reads the variable name above:

- **Python:** a pydantic-settings field `payments_api_key: SecretStr`, with no `env_prefix`.
- **TypeScript:** a key `PAYMENTS_API_KEY` in the zod env schema, exposed as `paymentsApiKey`.
- **Rust:** a struct field `payments_api_key`, read by `envy` or `config` without a prefix, wrapped in `secrecy::SecretString`.
- **Kotlin:** a config data class property `paymentsApiKey`, bound explicitly to `PAYMENTS_API_KEY` in the config module.
- **Scala:** a config case-class field `paymentsApiKey`, bound with a HOCON `${?PAYMENTS_API_KEY}` substitution.

**Other names:**

- **Labels on every resource:** `app=<repo>`, `env=<env>`, `role=<kind>`, `owner=<team>`. Label keys are 1 to 63 characters and start with a lowercase letter; values are 0 to 63 characters; both use lowercase letters, digits, `_` and `-`; at most 64 labels (labels docs).
- **Terraform:** local names and module call names are snake_case and name the kind (`google_cloud_run_v2_service.web`). The environment comes from a variable, never from an address.
- **Make targets:** kebab-case; the standard names in F are fixed. New targets put the family first (`secret-set`, `docker-build`, `test-integration`), so `help` groups them.
- **Globally unique names:** buckets share one global namespace and are 3 to 63 characters (Cloud Storage docs). If `<repo>-<kind>-<env>` is taken, append the project number.

**Limits checked:**

- Cloud Run service names: 49 characters or less (Cloud Run docs).
- Pub/Sub IDs: 3 to 255 characters, start with a letter, never start with `goog` (Pub/Sub docs).
- Artifact Registry repository and Cloud Run job name limits: verified at build time and added to the regex table.

**Regexes that `secrets check` enforces** (bash 3.2 `[[ =~ ]]`, ERE):

```text
env      ^(dev|staging|prod|pr-[0-9]{1,4})$
repo     ^[a-z][a-z0-9-]{1,9}[a-z0-9]$
kind     ^(web|worker|migrate|ci|deploy|images|files|tfstate|sql|secrets-rotation|[a-z][a-z0-9-]{0,8}[a-z0-9])$
resource ^<repo>-<kind>-<env>$          service-account names also <= 30 characters
secret   ^<repo>-[a-z][a-z0-9]*(-[a-z0-9]+)*-<env>$
envvar   derived: purpose with - to _ and upper-cased; must match ^[A-Z][A-Z0-9_]*$
db       ^<repo with - to _>_<env with - to _>$
```

**Worked example, `shop`:**

| Resource | dev | staging | prod |
| --- | --- | --- | --- |
| GCP project (recommended) | `shop-dev` | `shop-staging` | `shop-prod` |
| Web service and identity | `shop-web-dev` | `shop-web-staging` | `shop-web-prod` |
| Worker and identity | `shop-worker-dev` | `shop-worker-staging` | `shop-worker-prod` |
| Migrate job and identity | `shop-migrate-dev` | `shop-migrate-staging` | `shop-migrate-prod` |
| Extra service | `shop-transcribe-dev` | `shop-transcribe-staging` | `shop-transcribe-prod` |
| Images, files | `shop-images-dev`, `shop-files-dev` | `shop-images-staging`, `shop-files-staging` | `shop-images-prod`, `shop-files-prod` |
| Database | `shop_dev` | `shop_staging` | `shop_prod` |
| Secret, and its env var | `shop-payments-api-key-dev`, `PAYMENTS_API_KEY` | `shop-payments-api-key-staging`, `PAYMENTS_API_KEY` | `shop-payments-api-key-prod`, `PAYMENTS_API_KEY` |
| Rotation topic | `shop-secrets-rotation-dev` | `shop-secrets-rotation-staging` | `shop-secrets-rotation-prod` |

Project IDs are globally unique. If `shop-prod` is taken, add a suffix to the project only; resource names do not change.

**What a repository rename means.** Several GCP names are fixed at creation and cannot be renamed:

- secrets (their docs: "You can't edit the secret name or value and the replication policy");
- service account IDs ("can't change the ID after you create");
- buckets ("You cannot change the name of an existing bucket");
- Cloud Run service names ("cannot be changed later") and job names ("can't edit the name of the job").

Pub/Sub topics and Artifact Registry repositories have no rename either; this is recalled, and verified at build time. Postgres can rename a database in place (`ALTER DATABASE ... RENAME TO`) while nothing is connected to it. Terraform `moved` blocks change only state addresses, never cloud names.

**Runbook outline** (`common/docs/rename-repo.md`):

1. Pick the new `<repo>` short form and update the manifest in a branch.
2. Create the new identities, buckets, topic and secret containers with Terraform. The old ones stay.
3. Copy secrets with `secrets rename-repo` (D), and copy bucket contents with a storage transfer.
4. Deploy the services and jobs under the new names with the new identities, one environment at a time, starting with `dev`.
5. Move traffic: change domain mappings or load balancer backends.
6. After the rollback window, retire the old secrets, then delete the old services, identities, buckets and topic.
7. Rename the database last, or keep its old name and record it as a named exception in the manifest.

### C. The declaration: `secrets.manifest.json`

It lives at the root of each app repository and holds metadata only, never values. JSON was chosen because both `jq` and Terraform's `jsondecode` read it natively; Terraform has `yamldecode` but no TOML decoder (functions docs), and bash has no YAML parser. `common/secrets/manifest.schema.json` gives editors completion and validation, and the CLI enforces the same rules with `jq` (the authoritative check, because bash has no JSON Schema validator).

```json
{
  "schemaVersion": 1,
  "repo": "shop",
  "envs": ["dev", "staging", "prod"],
  "rollbackWindowDays": 7,
  "secrets": {
    "payments-api-key": {
      "description": "Payments provider secret key, used for charges and refunds",
      "owner": "billing",
      "readers": ["web", "worker"],
      "local": true,
      "rotationDays": 90,
      "probe": "probes/payments-api-key.sh"
    },
    "session-signing-key": {
      "description": "Signs session cookies",
      "owner": "platform",
      "readers": ["web"],
      "generated": { "bytes": 32 }
    }
  }
}
```

The fields:

- **`readers`:** the kinds whose service accounts get `secretAccessor`.
- **`local`:** the secret may be fetched by `dev-env` from the `dev` environment.
- **`probe`:** an executable that reads the value on stdin, checks it against the vendor API and exits 0 or 1. It never prints the value or puts it in argv: use `curl --config -` or `-H @-`, never `-u "$value"`.
- **`generated`:** Terraform generates the value (E).
- **`schemaVersion`:** independent of the release version.

Pinned versions live beside the manifest in `secret-versions/<env>.json` (`{"payments-api-key": "3"}`). Only the CLI writes them, and Terraform reads them.

### D. The CLI: `common/secrets/secrets`

The CLI is one bash script for bash 3.2+ (the macOS default), with `gcloud` and `jq` 1.6+ as its only dependencies. It runs from any stack. Its output is names, version numbers, dates and states, never values.

| Command | Who runs it | What it does |
| --- | --- | --- |
| `list [--env E]` | anyone, agents included | per secret: enabled versions, create dates, pinned version, readers from the IAM policy |
| `check [--env E]` | anyone, agents included | see the list after this table |
| `env-names` | anyone | prints the expected env var names, one per line, for stack drift tests |
| `set NAME --env E [--stdin] [--disable-previous]` | a human | see below |
| `rotate NAME --env E` | a human | idempotent across a rollout; see below |
| `retire NAME --env E` | a human | disables the versions older than the live one, once they are older than `rollbackWindowDays`; destruction follows by a later `retire --destroy` |
| `rename OLD NEW --env E [--apply]` | dry run: anyone; `--apply`: a human | see below |
| `rename-repo OLD_REPO NEW_REPO --env E [--apply]` | dry run: anyone; `--apply`: a human | plans every `<old>-...-<env>` secret at once and shows the old to new pairs and the manifest diff; `--apply` runs `rename` for each after one interactive confirmation |
| `dev-env -- CMD...` | a human | for each `local` secret in `dev`: reads the value into the shell with `export` (a builtin, so no argv), then `exec CMD`; nothing is written to disk |

**`check`:**

- Validates the manifest and the naming regexes (B).
- Compares declared secrets with Secret Manager: missing, undeclared, or no enabled version.
- Compares pins with versions: the pinned version exists and is enabled, and newer versions that are not rolled out are listed.
- Compares the live Cloud Run secret references with the pins, which catches an unapplied Terraform change.
- Reports overdue rotation (latest version older than `rotationDays`), retired-but-enabled versions, live resource names that break the naming rule, and missing agent deny rules in `.claude/settings.json`.
- Exits non-zero on drift.

**`set`:**

1. Refuses names that are not in the manifest.
2. Reads the value from a hidden prompt (`read -rs` on `/dev/tty`), or from stdin with `--stdin`. Without a TTY and without `--stdin`, it stops with "run this in your own terminal".
3. Runs the probe.
4. Runs `gcloud secrets versions add <secret> --data-file=-`, with the value on stdin.
5. Writes the new pin to `secret-versions/<env>.json`.
6. Prints the version number and the follow-up: "commit `secret-versions/<env>.json`; CI applies Terraform; then `make secret-check ENV=<env>`".

**`rotate`:**

- **First run:** does what `set` does.
- **A later run, after the rollout:** sees the live revision reading the new version, then disables the previous versions. The rollback window applies before destroy, not before disable, because disabling is reversible.

**`rename`, `--apply` (human):**

1. Checks that NEW is declared and valid.
2. Resolves OLD's newest enabled version explicitly, with `versions list --filter=state=ENABLED`, rather than relying on the `latest` alias.
3. Pipes `gcloud secrets versions access <v> --secret OLD | gcloud secrets versions add NEW --data-file=-`. The value is never printed, never on disk and never in argv.
4. Leaves OLD untouched, starting the alias period.
5. Prints the follow-up: update the manifest and Terraform, roll out revisions that read NEW, then `retire OLD` after the rollback window.

Only the newest enabled version is copied. Older versions are by definition retired or about to be, and copying them would spread exposure for no benefit; OLD stays readable for rollback during the alias period. The person renaming needs payload access to OLD, which no human holds standing in staging and prod (G). `rename` checks for it, and when it is missing prints the time-bound IAM grant an admin must make.

**Updates reach apps through pinned versions, not `latest`.** Cloud Run resolves environment-variable secrets at instance start, and Google recommends pinning them "instead of using `latest`". With `latest`, new instances of one revision would pick up a new value while older instances keep the old one: a mixed fleet, and a bad value surfaces only as instances scale. Pinning makes every rollout a reviewed change and every rollback a revert. The same pins apply to volume mounts (each mounted item names a version), the worker and the migrate job. The cost is one commit per rotation. The CLI writes the pin, so an agent can open that PR without ever seeing a value.

**Tests:** `common/secrets/test/*.bats` with bats-core 1.14.0, with a stub `gcloud` on `PATH` that records its argv and stdin to files.

- A planted value never appears in stdout, stderr or recorded argv, for `set`, `rotate`, `rename` and `dev-env`.
- Undeclared and badly named secrets are refused.
- `set` without a TTY and without `--stdin` fails.
- After `rename`, OLD stays until `retire`.
- `rename-repo` without `--apply` changes nothing.
- `check` reports each drift case.
- The regexes accept and reject a fixed table of names.

### E. Terraform module: `common/terraform/secrets/`

It needs Terraform 1.11 or later, for write-only arguments, and the Google provider 8.x (8.10.0 current). The input is `manifest_path`, `env`, `project` and `human_group`. It reads `jsondecode(file(var.manifest_path))` and `secret-versions/<env>.json`, and creates:

- **One `google_secret_manager_secret` per declared secret:** `secret_id` follows B, with `replication { auto {} }`, the labels from B, and `version_destroy_ttl` set to the rollback window.
- **Rotation:** `rotation { rotation_period, next_rotation_time }` with `topics` pointing to `<repo>-secrets-rotation-<env>`. The provider requires `topics` for rotation, and `next_rotation_time` whenever a period is set. Secret Manager does not rotate anything itself: it only publishes a `SECRET_ROTATE` message, the period is at least one hour, and the first time is at least five minutes ahead. The module sets `next_rotation_time` once and ignores later changes to it. The topic grants publish to the Secret Manager service agent, as its docs require (exact binding verified at build), and feeds the team's alert channel.
- **IAM, per secret:**
  - `roles/secretmanager.secretAccessor` for each reader's `<repo>-<kind>-<env>` service account;
  - `secretVersionManager` and `viewer` for the human group (add, enable and disable versions, no payload access);
  - `viewer` for `<repo>-ci-<env>` (metadata only);
  - accessor for the human group in `dev` only, and only on `local` secrets.
- **Never values, with one exception.** For `generated` secrets, an ephemeral `random_password` feeds `google_secret_manager_secret_version.secret_data_wo`. Write-only arguments are "never persisted to plan or state" (Terraform docs). The provider added `secret_data_wo` in 6.23.0, and since 8.0.0 `secret_data_wo_version` is a string required together with it. The CLI bumps that version to regenerate.
- **An output map** from env var name to `{secret, version}`. A stack's Cloud Run Terraform uses it for `value_source.secret_key_ref` or for volume items. `examples/cloud-run/` shows a web service, a worker and a migrate job using it.

`terraform validate` and a `terraform plan` against a stub project run in CI with `-backend=false`. A test asserts no secret value appears in the plan JSON for a generated secret.

### F. Make contract: `common/make/`

- **`common.mk`:**
  - shell flags (`SHELL := bash`, `-eu -o pipefail -c`) and `MAKEFLAGS += --warn-undefined-variables --no-builtin-rules`;
  - `.DEFAULT_GOAL := help`, with a `help` target that prints every `## description`;
  - `ENV ?= dev`.
- **`secrets.mk`:** `secret-set`, `secret-list`, `secret-check`, `secret-rotate`, `secret-retire`, `secret-rename`, `secret-rename-repo` and `dev-real`, each a one-line call to the CLI with `NAME`, `OLD`, `NEW` and `ENV`. `dev-real` runs `secrets dev-env -- $(DEV_CMD)`.

Each stack's Makefile does `include tools/common/make/common.mk tools/common/make/secrets.mk`, then defines `DEV_CMD` and the standard targets for its toolchain. Every standard target exists in every repo; a target with nothing to do prints "not applicable" and exits 0.

| Target | Next.js | FastAPI |
| --- | --- | --- |
| `setup` | `pnpm install --frozen-lockfile` | `uv sync --locked`, `prek install` |
| `dev` | `pnpm dev` | `uv run fastapi dev` |
| `lint`, `format` | `pnpm lint`, `pnpm format` | `ruff check`, `ruff format` |
| `typecheck` | `pnpm typecheck` | `mypy` |
| `test`, `test-integration` | `pnpm test`, `pnpm e2e` | `pytest tests/unit`, `pytest tests/integration` |
| `arch` | `pnpm arch && pnpm arch:baseline` | `lint-imports` plus `tests/architecture` |
| `check` | `pnpm check` | all of the above plus the FastAPI drift tests |
| `migrate`, `run-worker` | `pnpm db:migrate`, the worker entry (1.1.0) | `alembic upgrade head`, `procrastinate worker` |
| `docker-build` | `docker build` per target | `docker build` per target |

Other stacks map the same names:

- **Rust (cargo):** `cargo fmt`, `cargo clippy -D warnings`, `cargo test`, `cargo deny check`.
- **Kotlin (Gradle):** `./gradlew ktlintCheck detekt test`, with ArchUnit for `arch`.
- **Scala (sbt):** `sbt scalafmtCheckAll scalafixAll test`.

### G. AI agents

- **Allowed for agents:** `make secret-list`, `make secret-check`, and `secret-rename` or `secret-rename-repo` without `APPLY=1` (dry runs). They may write the pin-file PR that the CLI prepared.
- **Asked of the human:** `secret-set`, `secret-rotate`, `secret-retire`, rename with `APPLY=1`, and `dev-real`. The human types the value in their own terminal. A hidden prompt needs a TTY, and an agent's shell has none, so `set` fails safely there.
- **The real boundary is credentials, not rules.** An agent session runs with no gcloud credentials, or with a separate gcloud config (`CLOUDSDK_CONFIG`) whose identity holds only `secretmanager.viewer`. Code that runs with a secret can read it, so real credentials are used only in a separate context the agent cannot steer.
- **Accident guards,** shipped as `common/agents/claude-settings.json` for each stack to merge, and checked by `secrets check`:
  - deny `Bash(gcloud secrets versions access *)`, `Bash(printenv*)`, `Bash(env)`, `Bash(make dev-real*)`, `Bash(make secret-set*)`, `Bash(make secret-rotate*)`, `Bash(* APPLY=1*)`;
  - deny `Read(./.env)` and `Read(./.env.*)`, with `Read(!./.env.example)` after them;
  - the sandbox on, with `denyRead` for the same paths.

  Claude Code's docs say Read deny rules do not cover arbitrary subprocesses, so the sandbox is the OS-level half. `common/agents/AGENTS.md` states the same rules in tool-neutral words.

### H. CI/CD

- **Authentication:** CI authenticates through Workload Identity Federation as `<repo>-ci-<env>` (build, push, `secret-check` with viewer) and as `<repo>-deploy-<env>` (Terraform apply and new revisions). Neither can read payloads.
- **Deploys** reference secrets by name and pinned version through Terraform.
- **No secret values in CI variables.** The only exception is a value a vendor forces into CI with no OIDC alternative (for example, a third-party registry or an error-tracker upload token). Each exception is listed in the manifest as `"ci": true` with a reason, scoped to the one job that needs it, and reported by `check`.

### I. How a project gets it

The app vendors it by copying `common/` into `tools/common/` with its `VERSION` file. Nothing is fetched over the network at run time. An upgrade replaces the folder and follows `common/CHANGELOG.md`. `secrets check` warns when `tools/common/VERSION` is older than the manifest's `schemaVersion` supports.

## Risks

- **The secrets CLI is GCP-only in 1.0.0.** The backend seam is kept small and documented.
- **Bash 3.2 lacks associative arrays.** All structured data goes through `jq`, and the code avoids bashisms beyond 3.2, checked by running the tests under `/bin/bash` on macOS.
- **Pinning costs a commit per rotation.** This is accepted for reviewability; the CLI prepares the change.
- **A repository rename is a migration, not a rename.** The runbook makes it explicit, and `rename-repo` covers only the secrets part.
- **Vendor probes call external APIs.** They are optional, run only in `set` and `rotate`, and never in CI.
