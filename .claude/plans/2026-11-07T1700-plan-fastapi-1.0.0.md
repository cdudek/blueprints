# FastAPI blueprint 1.0.0: the modular monolith with doors, in Python

## Why

The Next.js blueprint carries one architecture (a modular monolith whose modules are entered only through doors) as a document plus a runnable template that enforces it. Python services need the same, so a team running both stacks reads one set of principles. The research of 2026-11-07 found the concepts map: a package with `__init__.py` is a module, import-linter can express the structural rules, and what does not map is dropped (the browser/server split) or replaced by the Python idiom (exceptions instead of `Result`, a top-level `tests/`).

Owner decisions (2026-11-07): one package `src/app/`; Python `>=3.14`, run 3.14; `architecture.toml` (pydantic-validated) generates the import-linter config, with a drift test and baselines as `ignore_imports` lines that only shrink; and as defaults Procrastinate, psycopg 3, domain exceptions, mypy strict, async SQLAlchemy 2, services as plain functions taking `tx` and `principal`, real Postgres in tests, no duplication gate yet.

Revision 1 (owner review) moves the weight from tool choice to the things that make or break a service: who owns a transaction, how a payment survives a crashed worker, how a deploy runs old and new code side by side, and what each check really proves. The first milestone is a worked slice that proves those; the policy generator is derived from it afterwards.

Release: a new blueprint `fastapi/`, version 1.0.0, own changelog. The Next.js blueprint is not edited.

## Scope

### A. Principles shared with Next.js

`fastapi/ARCHITECTURE.md` section 2 uses the same wording as the Next.js 1.1.0 principles: cut along decisions likely to change (Parnas); the top level shows the domain; dependencies point one way and never cycle; a small public surface per module; each module owns its data; boundaries need a tool, adopted with a baseline that only shrinks; parse at the edge, then trust the types; pure core, side effects at the shell; abstract only what really varies; don't distribute early.

Python specifics, each with its rule:

- **The door is `__init__.py`, and a convention plus checks make it a boundary.** `__all__` only defines what `from pkg import *` imports (Python tutorial, "Importing from a package"); it does not stop `from app.modules.orders.repository import x`. The boundary comes from import-linter contracts and a door-export test (section C). No star imports, no aliases, no declarations in a door; `modules/__init__.py` stays empty.
- **Role doors exist only when a module needs them.** `router.py` (HTTP, imported only by `api/`), `system.py` (webhook and job operations), `jobs.py` (worker tasks). In the example, `orders` has only `router.py`; `billing` has all three.
- **One owner per transaction** (section B). Operations take a `Tx`; they never commit.
- **`Depends` at the edge only.** Routers and `shared/http.py`; services get `tx` and `principal` as arguments. No container.
- **Expected failures are exceptions with a closed code.** `DomainError` subclasses with `code: Literal[...]`, exported by the door, mapped by `api/` to problem-detail JSON (RFC 9457).
- **ORM models are private.** Cross-module foreign keys are strings, never `relationship()`; data crosses a door as a schema.
- **Settings is the only reader of the environment;** credentials are `SecretStr` (section E).
- **One package, not a flat `src/`.** pytest's good practices and uv's default application layout use `src/<package>/`; one namespace keeps `config`, `clients`, `shared` and `modules` (all on PyPI) from becoming top-level import names; import-linter's root package and layers stay one line. Cost: one path segment. The docs give the flat-`src/` mapping for teams with that house rule.

### B. Transactions, retries and the worked slice (milestone 1)

**B1. Transaction ownership.** Exactly one place owns commit and rollback per atomic use case: the entry point. That is a router handler calling one operation, a workflow in `workflows/`, or a job handler in `jobs.py`. It opens `async with in_transaction() as tx:` and passes `tx` down. Operations take `tx: Tx` as a required argument and never open, commit or roll back; repositories take `tx` and never commit. `in_transaction()` raises if a transaction is already open (no hidden nesting). `orders.create()` followed by a failing `billing.request_payment()` is therefore one transaction, owned by the `place_order` workflow, and both writes roll back together. Checks: an AST rule allows `.commit()`, `.rollback()` and `.begin()` only in `db/`, and `in_transaction(` only in `api/`, `*/router.py`, `workflows/` and `*/jobs.py`; import-linter keeps `async_sessionmaker` inside `db/`; a runtime test proves nesting raises.

**B2. Processes that span transactions.** Anything with an external call is several transactions with named intermediate states, stored as a database enum, and a resume or compensation rule per state. No transaction is open during an external call.

**B3. The worked slice: order, durable payment request, worker, result.**

1. `POST /v1/orders` calls the `place_order` workflow. In one transaction: `orders.create()` writes the order as `pending_payment`; `billing.request_payment()` writes a `payment_requests` row (`status = requested`, `idempotency_key` generated once, unique); a Procrastinate job is deferred as a wake-up. The row is the durable intent. If the job deferral cannot join the SQLAlchemy transaction (build spike), a lost wake-up is harmless: a periodic sweeper defers jobs for `requested` rows older than a threshold.
2. The job `billing.process_payment_request(request_id)`, transaction 1: a conditional update claims the row (`requested` or stale `processing` to `processing`, `attempts + 1`) and commits. Zero rows changed means someone else has it: stop.
3. Outside any transaction: `payments.charge(amount, reference=request_id, idempotency_key=row.idempotency_key)`.
4. Transaction 2: conditional update to `succeeded` with the provider reference, and `orders.mark_paid(tx, ...)`; commit. A lost conditional update is reloaded and recomputed, never reported as success.

**Retry rules.** The key belongs to the request row and never changes; a new key only comes with a new request (a new user-initiated attempt). Transient errors and unknown outcomes (timeout after send) retry with backoff and the same key. A definite decline sets `failed` and the order `payment_failed`, no retry. After the maximum attempts the row goes to `needs_attention` and logs an alert-level event. A worker that dies leaves its job `doing`; Procrastinate workers heartbeat every 10 seconds, and the template ships the documented periodic task that retries stalled jobs (`get_stalled_jobs`, `retry_job`). Compensation: cancelling a paid order defers a refund job with its own request row and key.

**Provider contract.** The payments port requires idempotency keys. A provider without them must look up a charge by our reference before charging; the port docstring says so and the fixture provider implements key semantics (it records charges by key and returns the first result for a repeated key), which makes it the test oracle. The fixture provider also takes a fault hook: "raise after charging".

**Slice tests** (real Postgres, real commits, separate connections):

- **Payment succeeded, worker died before recording it:** the fault hook raises after the charge; the stalled-job retry runs the job again; assert exactly one charge, request `succeeded`, order `paid`.
- **Two workers race for one request** on two connections: one charge, one claim.
- **Decline**, **unknown outcome then success**, **maximum attempts** reaching `needs_attention`.
- **`place_order` fails in `billing.request_payment()`:** neither row exists.

**Test database strategy.** Repository and service tests keep a transaction per test and roll back. Worker and concurrency tests cannot: under Read Committed, Postgres's default, a query "never sees either uncommitted data or changes committed by concurrent transactions during the query's execution" (PostgreSQL docs 13.2.1), so a second connection or the worker would not see test data. They commit for real on a database cloned per test module from a migrated template (`CREATE DATABASE ... TEMPLATE`), dropped afterwards. testcontainers locally, a service container in CI.

### C. Guarantees and the coverage matrix (milestone 2, built first in it)

The matrix lives in `ARCHITECTURE.md` and drives the docs: no sentence in the blueprint promises more than its row. Each row says what is detected, what stays review, and which exceptions are allowed (each exception is recorded in the policy log, section D4).

| Guarantee | Detected by | Not detected (review) | Allowed exceptions |
| --- | --- | --- | --- |
| Other modules enter only through the door | import-linter contract per module, over every import form | `importlib` and string imports | brownfield baseline pairs |
| A door exports only operations, schemas and errors | reflection: functions must carry `@operation`; classes must be `BaseModel` subclasses defined in `schemas.py` or `DomainError` subclasses in `errors.py`; anything else fails | what an operation does with its access policy | none |
| Role doors are imported only by their callers | import-linter `protected` | none | none, never baselinable |
| Every route is authenticated | test over `app.routes` dependants for a `require_*` dependency | resource checks inside the operation (behaviour test per operation) | public allowlist in the policy |
| One transaction owner | AST call-name rule (B1) and the nesting test | `COMMIT` in raw SQL text | none |
| No external call inside a transaction | AST: calls inside an `async with in_transaction()` body to names imported from `app.clients` or `httpx`; helpers are not followed | calls through helper functions, raw sockets | none |
| `rules.py` is pure | import-linter `forbidden` with indirect imports, plus AST ban on `datetime.now`, `random`, `uuid4`, `os`, `time`, `open` | impure code in an allowlisted package | packages listed in the policy |
| No blocking call in async code | ruff `ASYNC`, which knows a list of blocking APIs | arbitrary blocking or CPU-heavy code in called libraries | counted `noqa` lines |
| Only `config/` reads the environment | ruff TID251 bans `os.environ` and `os.getenv` | env access through third-party libraries | none |
| One owner per table | reflection over `Base.metadata` against the policy | raw SQL touching another module's table; `text(` call sites are listed for review | read exceptions in the policy |
| Expand migrations are additive | AST over `op.*` calls (no drop, rename, `NOT NULL` tightening, type narrowing) | `op.execute()` raw SQL: allowed only with a `# reviewed: <reason>` marker, listed in CI output | marked raw SQL |
| One charge per payment request | slice tests (B3) | providers without idempotency support | none |
| Suppressions only shrink | suppression ratchet (D1) | none | policy-log entries |
| Baselines only shrink, policy never loosens silently | `baseline_shrinks.py`, `policy_changes.py` (D4) | none | policy-log entries |
| No secrets committed | gitleaks hook and full-history CI scan; ruff S105 to S107 | secrets in runtime output beyond the redaction list | `.gitleaksignore` fingerprints, counted |
| Mounted secret files win over env | settings test with conflicting values (E) | none | none |
| Declared secrets match `Settings` | drift test against `secrets env-names` (E4) | none | none |
| Readiness means schema compatibility | readiness tests (F) | none | none |

Every detected row has a deliberate-violation fixture under `tests/fixtures/arch/<rule>/`, a clean twin, and an exact-message assertion. Never-baselinable: role-door protection, env reads, framework imports in `service`, `repository` or `rules`, transaction ownership. A stated limit: import-linter baselines are per module pair, so a second violation of a pair in the same file is invisible.

**Tool choice for these checks.** import-linter 2.16 is the only import-graph enforcer. PyTestArch 5.1.0 ("generally inspired by ArchUnit") is not shipped: it scans imports only, the same evidence import-linter uses, so it would be a second policy and a second baseline for no new rule. tach 0.35.3 is not shipped: pre-1.0 and no baseline. The rules import-linter cannot express are plain pytest tests in `tests/architecture/` using reflection, the AST and grimp (import-linter's graph library): the ArchUnit-style half, as ArchUnitTS is in the Next.js template.

### D. Tooling

**D1. Lint and format.** ruff 0.17.4 (`ruff format`, line length 100), every family explicit with a one-line reason in `pyproject.toml`, no `ALL`, no preview rules:

- `E`, `W`, `F`, `I`: real errors and stable import order.
- `UP`, `B`, `SIM`: 3.14 syntax, bugbear's likely bugs, simplifications.
- `S` (bandit): hardcoded passwords S105 to S107, SQL from strings S608, subprocess S602 and S603, `verify=False` S501, pickle S301. `S101` off under `tests/**` only.
- `C90`, `PLR0911`, `PLR0912`, `PLR0913`, `PLR0915`, `PLR0917`: complexity and size, replacing radon (last release 2023). Ruff defaults; raising one needs a reason.
- `ASYNC`: known blocking calls in `async def` (a list, not a proof; see C).
- `FAST`: FAST001 to FAST003; FAST002 forces `Annotated` dependencies, which also removes bugbear's B008 conflict.
- `TID`: TID252 bans `..` imports; TID251 bans `os.environ`, `os.getenv`, `requests`, with a per-file ignore for `src/app/config/**`.
- `PT`, `RUF`, `T20`, `DTZ`, `BLE`, `LOG`: pytest style; ruff's rules including RUF100; no `print`; no naive datetimes; no blind `except`; no logging misuse.

Not selected: `ANN` (mypy covers it), `D` (noise), `ERA`, `TRY`, `EM`, `FBT` (style, high false-positive rate), full `PL`. Ruff has no pydantic family; mypy's `pydantic.mypy` plugin covers models.

**Suppression ratchet.** RUF100 flags `noqa` directives "that are no longer applicable" (ruff docs); it does not stop a new, valid `noqa`. So `scripts/quality/suppressions.py` counts `# noqa`, `# type: ignore`, `per-file-ignores` entries and `.gitleaksignore` lines per file and code, compares with the merge base, and fails on any increase without a policy-log entry.

**D2. Types and dependencies.** mypy 2.4.1 strict with the pydantic plugin. Switching is an option with criteria, not scheduled. pyrefly 1.4.1 (README: "development status is stable", built-in pydantic support, `pyrefly init` from mypy) qualifies when it runs clean on the template, reports every finding of the mypy type fixtures, and handles `Mapped[]` and pydantic models without suppressions. ty 0.0.99 (README: "currently in beta", "no stable API") qualifies after a stable release, by the same test. Never two blocking type checkers. deptry 0.25.1 gates missing, unused, transitive and misplaced dev dependencies.

**D3. Hooks.** prek 0.5.10 reads the standard `.pre-commit-config.yaml` (it is a reimplementation of pre-commit; ruff, FastAPI and CPython use it), with no prek-only features, so pre-commit 4.7.0 stays a fallback. Hooks are `repo: local` and run through `uv run`, so versions come from `uv.lock`. pre-commit runs ruff `--fix`, ruff format, gitleaks on staged changes and `uv lock --check`; pre-push runs `make lint typecheck arch`.

**D4. Policy, baselines and the policy log** (milestone 3). `architecture.toml` carries `schema_version = 1`, an integer for the file format, independent of the blueprint release; the loader refuses an unknown version. A loosening can make a shrinking baseline meaningless, so `policy_changes.py` fails, compared with the merge base, on any of these without a matching entry (reason, date) in `quality/policy-log.toml`:

- a new edge, read exception, exemption, public route or rules-allowlist package;
- a removed or narrowed contract;
- a raised lint threshold or a new per-file ignore;
- a new baseline line, or a suppression count increase.

`baseline_shrinks.py` fails closed (unparseable file or git error fails) when a baseline grows.

**D5. Makefile contract.** `.DEFAULT_GOAL := help`, `SHELL := bash` with `-eu -o pipefail -c`, `--warn-undefined-variables --no-builtin-rules`, every target `.PHONY`, a `## description` per target that `help` prints. Targets are one-line wrappers over `uv run`; longer logic is a script. CI calls the same targets.

### E. Secrets (the Python side)

The secrets workflow is stack-agnostic and lives in the common 1.0.0 plan (`2026-11-07T1730-plan-common-1.0.0.md`): the keyless-first principle, naming (`<repo>-<purpose>-<env>`, env var `PAYMENTS_API_KEY`), `secrets.manifest.json`, the bash CLI (`set`, `list`, `check`, `rotate`, `retire`, `rename`, `rename-repo`, `dev-env`), the Terraform module, pinned versions, CI through Workload Identity Federation, and the agent rules. The template vendors it as `tools/common/` and includes `secrets.mk`. This section keeps only what is specific to Python.

1. **Keyless database.** Production connects through the Cloud SQL Python connector with `psycopg` and `enable_iam_auth=True`, so there is no database password; local and test databases use the compose password. `db/` hides the difference behind one engine factory.
2. **No secrets locally by default.** Every client has `fixture` and `noop` providers; `fixture` is the default outside production. `make dev-real` (human-run, from `secrets.mk`) is the only way to start with real `dev` values.
3. **Settings.** pydantic-settings gives env vars and dotenv "priority over values loaded from the secrets directory" by default. Because the template mounts secrets as files, `Settings.settings_customise_sources` returns `(init_settings, file_secret_settings, env_settings)`, with no dotenv source in production. A test sets conflicting values in both and asserts the file wins. Field names follow the common naming rule with no `env_prefix` (`payments_api_key: SecretStr` reads `PAYMENTS_API_KEY`), `secrets_dir` defaults to `/run/secrets`, and `extra="forbid"`. `.get_secret_value()` is called only inside the client that uses the value. A validator fails closed in production on a missing secret.
4. **Drift test.** The `SecretStr` fields of `Settings` must equal `tools/common/secrets/secrets env-names`, and `.env.example` must list exactly the non-secret settings plus those names, without values.
5. **Output.** A structlog processor masks keys matching `password|secret|token|api_key|authorization|cookie` and every `SecretStr`, tested with a planted value; settings are never logged whole. gitleaks 8.30.1 runs on staged changes and over the full history in CI; a test plants a fake key and expects failure.
6. **Agents.** `.claude/settings.json` merges `tools/common/agents/claude-settings.json`, and `common`'s `secrets check` verifies the deny rules are present. These rules guard against accidents. The boundary is that agents hold no credentials and real values run only in a context the agent cannot steer (common plan G).

Encrypted files in the repo (sops, git-crypt, dotenvx) are not used. The comparison and verdict from revision 1 move to `common/README.md`.

### F. Deploys: expand/contract and readiness (milestone 2)

**Sequence**, written into `ARCHITECTURE.md` and `docs/deploy.md`:

1. Expand: the migrate job applies additive migrations only.
2. Deploy the new web and worker versions next to the old ones; both run against the expanded schema.
3. Shift traffic to the new web version.
4. Stop the old web and old worker versions; workers shut down gracefully and stalled jobs are retried.
5. Wait out the rollback window. Rollback means shifting traffic back to the old version, which still works because only expand ran.
6. Contract in a later release, after no running version uses the object. The contract PR names the release that removed the last use.

Job payloads change only additively. A renamed task keeps its old name registered until old workers are gone.

**Readiness checks compatibility, not the exact head.** An exact-head check would mark old instances unready after step 1, although they work. Instead, `env.py` uses Alembic's `on_version_apply` hook to append each applied revision to a `schema_history` table. The app declares `REQUIRED_REVISION`, the newest migration its code needs. `/readyz` checks a database ping and that `REQUIRED_REVISION` is in `schema_history`. Old instances stay ready; a new instance before its migration is not. The exact migration state is checked separately by the deploy pipeline (`alembic current --check-heads` after the migrate job). `/healthz` checks the process only. Tests cover old-ready, new-not-ready-before-migrate and new-ready-after.

## Build steps

One commit per step on `feat/fastapi-1.0.0`, tests green before the next.

**Milestone 1: the worked slice.**

1. Skeleton: `pyproject.toml`, `uv.lock`, the Makefile, ruff, mypy and prek config, `compose.yaml`, `config/settings.py` with the source order and its conflict test, `main.py` with lifespan and `/healthz`.
2. `db/` with `Tx`, `in_transaction()` and the nesting test; Alembic async with `schema_history`; the `orders` module with `router.py` only; per-test-rollback repository tests.
3. `billing` (`payment_requests`, states, `request_payment`, `system.py`, `jobs.py`), `clients/payments` with the idempotent fixture provider and its fault hook, and the `place_order` workflow with its rollback test.
4. Worker: Procrastinate app, `process_payment_request`, the sweeper and the stalled-job retry, retry rules. The spike on deferring inside the SQLAlchemy transaction runs first; its result goes in the decision log.
5. Slice tests (B3) on committed data and separate connections; `docs/worked-slice.md`.

**Milestone 2: guarantees.**

6. Coverage matrix (C) as the first draft of `ARCHITECTURE.md` section 9; a hand-written `.importlinter` for the two modules; the reflection and AST tests from C, each with a fixture, a clean twin and an exact message.
7. Ratchets and contracts: the suppression ratchet, deptry, the openapi drift test, `alembic check`, the migration phase test, `tests/tooling/` in `make check`.
8. Secrets, Python side (E). Needs common 1.0.0 merged. Vendor `tools/common/`, add `secrets.manifest.json` with `payments-api-key`, the settings source-order and drift tests, the Cloud SQL connector engine factory, redaction, the gitleaks hook and planted-key test, and `.claude/settings.json` merged from common.
9. Deploys (F): `schema_history`, readiness tests, Dockerfile with three targets, `docs/deploy.md`, CI workflow and Docker build smoke.

**Milestone 3: derived tooling and release.**

10. `architecture.toml` with its pydantic model and `schema_version`; the generator, whose first test reproduces the hand-written `.importlinter` from step 6 exactly before the file becomes generated; the drift test; `baseline_shrinks.py`, `policy_changes.py`, `quality/policy-log.toml`, `make arch-baseline-write`.
11. `ARCHITECTURE.md` and `README.md` finalised on the example (H), the root README row, CHANGELOG, a full `make check` on a fresh copy, then one PR to `cdudek/blueprints` from `feat/fastapi-1.0.0` into `main`, which the owner merges.

## Risks

- **Procrastinate's maintenance.** Its README asks for maintainers, though 3.10.0 shipped 2026-09. Jobs sit behind `jobs.py` doors and the row is the durable intent, so swapping in pgqueuer touches the doors and `worker.py` only.
- **Providers without idempotency keys** need the look-up-before-charge path; the port contract says so, and the slice proves only the keyed path.
- **AST rules see names, not behaviour.** Helpers and raw SQL are review items, listed in the matrix rather than promised.
- **Real-commit tests are slower.** The template-database clone keeps them isolated and parallel per module.
- **Agent guards are accident protection.** The boundary is that agents hold no credentials (common plan G).
- **Dependency on common.** Milestone 2 waits for common 1.0.0. The vendored copy pins the version, so later common releases never break the template silently.
- **make on Windows.** The docs name WSL, or `uv run` with the commands from the target table.
- **Scope.** Down from 11 tooling-heavy steps to three milestones; the diagram, module generator and rename handling wait until an app needs them.
