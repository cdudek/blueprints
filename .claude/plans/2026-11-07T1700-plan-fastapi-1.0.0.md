# FastAPI blueprint 1.0.0: the modular monolith with doors, in Python

## Why

The Next.js blueprint carries one architecture (a modular monolith whose modules are entered only through doors) as a document plus a runnable template that enforces it. Python services need the same thing, so a team that runs both stacks reads one set of principles and gets the same guarantees from CI. The research of 2026-11-07 found that the concepts map cleanly: a package with `__init__.py` and `__all__` is a door, and import-linter can express every structural rule the Next.js template builds by hand. What does not map is dropped (the browser/server split), or replaced with the Python idiom (exceptions instead of `Result`, a top-level `tests/` instead of colocated tests).

The owner decided on 2026-11-07:

1. Layout: one package, `src/app/`.
2. Python `>=3.14`, run on 3.14.
3. Policy: `architecture.toml` (validated by a pydantic model) generates the import-linter config; a drift test fails on a stale config; baselines are `ignore_imports` lines that only shrink.
4. All other research recommendations are defaults: Procrastinate, psycopg 3, domain exceptions, mypy strict, async SQLAlchemy 2, services as plain functions taking `session` and `principal`, real Postgres in tests (testcontainers locally, a service container in CI), no duplication gate yet.

This plan adds what the owner asked for on top: a curated linter set, ArchUnit-style tests, a Makefile contract and a secrets standard that keeps AI agents safe.

Release: a new blueprint, `fastapi/`, version 1.0.0, with its own changelog. The Next.js blueprint is not edited.

## Scope

### A. Principles shared with Next.js

`fastapi/ARCHITECTURE.md` section 2, "Principles", uses the same wording as the Next.js 1.1.0 principles section, so both read as one rulebook:

- Cut along decisions that are likely to change (Parnas).
- The top level shows the domain (screaming architecture).
- Dependencies point one way and never cycle.
- A module has a small public surface and keeps the rest private.
- Each module owns its data.
- Boundaries need a tool, adopted with a baseline that only shrinks.
- Parse at the edge, then trust the types.
- Pure core, side effects at the shell.
- Abstract only what really varies.
- Don't distribute early.

Python specifics follow, each with its rule and the reason it differs from Next.js:

- **One runtime, so one public door.** `__init__.py` with an explicit `__all__` is the door (PEP 8). Role doors take one kind of caller each: `router.py` (HTTP assembly), `system.py` (webhook and job operations), `jobs.py` (worker tasks). There is no `public.ts`/`server.ts` pair.
- **The door is the only barrel.** `modules/__init__.py` stays empty. No star imports, no aliases, no declarations in a door.
- **`Depends` at the edge only.** Routers and `shared/http.py` use it; services get `session` and `principal` as plain arguments. No container.
- **Expected failures are exceptions with a closed code.** Each is a subclass of `DomainError` with a `code: Literal[...]`. The door exports them, and `api/` maps them to problem-detail JSON (RFC 9457). The rule "a lost update is reloaded and recomputed, never reported as success" stays.
- **ORM models are private.** Foreign keys across modules are strings, never `relationship()`. Data crosses a door as a schema.
- **Async all the way, never blocking.** Blocking calls in `async def` are lint errors. CPU-bound work goes to the worker.
- **Settings is the only reader of the environment.** Secrets are `SecretStr` (section D).
- **The layout deviates from a flat `src/`.** The template uses one package, `src/app/`, because pytest's good-practices page and uv's default application layout both use `src/<package>/`; one namespace stops `config`, `clients`, `shared` and `modules` (all four exist on PyPI) from becoming top-level import names; and import-linter's root package and layer containers stay one line each. The cost is one path segment (`app.modules.orders`); the folder vocabulary stays. A team with a flat-`src/` house rule gets the mapping in the docs: `package = false`, `pythonpath = ["src"]`, every top-level name a root package.

A "where the sources disagree" note covers four choices: barrels versus PEP 8, relative versus absolute imports, `Result` versus exceptions, and colocated versus separate tests.

### C. Rules and tooling

**C1. Linter and type checker.** ruff 0.17.4 does both linting and formatting (`ruff format`, line length 100, `docstring-code-format = true`). There is no `select = ["ALL"]` and no preview rules. Every family is listed explicitly, with its reason in a comment in `pyproject.toml`:

- `E`, `W`, `F`, `I`: pycodestyle, pyflakes and import order; real errors and stable diffs.
- `UP`, `B`, `SIM`: pyupgrade to 3.14 syntax (target read from `requires-python`); bugbear's likely bugs (mutable defaults, `raise` without `from`, loop-variable closures); simplifications.
- `S`: flake8-bandit, the security rules. They cover hardcoded passwords (S105 to S107), SQL built from strings (S608), subprocess with a shell (S602, S603), `verify=False` (S501) and pickle (S301). `S101` (assert) is off only under `tests/**`. This replaces running bandit separately.
- `C90` and `PLR0911`, `PLR0912`, `PLR0913`, `PLR0915`, `PLR0917`: complexity and size limits (all stable rules). These replace radon, whose last release, 6.0.1, came out in 2023. The thresholds are the ruff defaults. Raising one needs a reason in the config comment.
- `ASYNC`: blocking calls inside `async def`, the main FastAPI footgun.
- `FAST`: the FastAPI rules (FAST001 redundant `response_model`, FAST002 non-`Annotated` dependency, FAST003 unused path parameter). FAST002 forces `Annotated`, which also removes bugbear's B008 conflict with `Depends()` defaults.
- `TID`: TID252 bans `..` relative imports (sibling `.x` stays allowed); TID251 bans `os.environ`, `os.getenv` and `requests` (use `httpx`), with a per-file ignore for `src/app/config/**` only.
- `PT`, `RUF`: pytest style; ruff's own rules, including RUF100, which makes a stale `# noqa` an error so suppressions only shrink.
- `T20`, `DTZ`, `BLE`, `LOG`: no `print` (use the logger), no naive datetimes, no blind `except Exception`, no stdlib logging misuse.

Not selected: `ANN` (duplicates mypy strict), `D` (noise; the workflow header is an architecture test), `ERA`, `TRY`, `EM`, `FBT` (style, high false-positive rate), full `PL` (overlaps mypy).

ruff has no pydantic rule family (checked on the rules page, 2026-11-07). Pydantic is covered by mypy's `pydantic.mypy` plugin with `init_forbid_extra`, `init_typed` and `warn_required_dynamic_aliases`. SQLAlchemy 2 `Mapped[]` needs no plugin.

- **Type checker:** mypy 2.4.1 strict, as decided. State on 2026-11-07: ty 0.0.99's README says "ty is currently in beta" with "no stable API; breaking changes, including changes to diagnostics, may occur between any two versions"; pyrefly 1.4.1's README says "development status is stable", it is the default checker for a 20-million-line codebase, has built-in pydantic support, and `pyrefly init` migrates from mypy. When to switch (decision log): pyrefly is a candidate now, by trial: it runs clean on the template, catches every mypy finding in the type fixtures, and handles `Mapped[]` and the pydantic plugin's checks without suppressions; if the trial passes at 1.1.0, pyrefly replaces mypy (never both as gates). ty is re-evaluated when it ships a stable release with a stable diagnostics API, under the same trial.
- **Dependency hygiene:** deptry 0.25.1 fails on missing (DEP001), unused (DEP002), transitive (DEP003) and misplaced dev (DEP004) dependencies. vulture finds dead code against `quality/vulture-whitelist.py`, a FastAPI-aware whitelist that only shrinks. Its role is knip's in the Next.js template.
- **Hook runner:** prek 0.5.10 with the standard `.pre-commit-config.yaml`. prek is a Rust reimplementation of pre-commit that reads the same config; ruff, FastAPI and CPython use it. The template uses no prek-only features, so `pre-commit` 4.7.0 stays a drop-in fallback. Hooks are `repo: local` and run `uv run ruff ...`, so versions come from `uv.lock`, not a second pin. pre-commit: ruff check `--fix`, ruff format, gitleaks on staged changes, `uv lock --check`; pre-push: `make lint typecheck arch`. Not lefthook: it would add a Go binary and a second config dialect to a Python repo.

**C2. Architecture enforcement: import-linter plus ArchUnit-style pytest rules.**

The three candidates, as of 2026-11-07:

- **import-linter 2.16:** `forbidden`, `protected`, `layers`, `independence` and `acyclic_siblings` contracts over the import graph; `ignore_imports` with alerting on unmatched lines, so a stale baseline line fails; indirect imports checked by default.
- **PyTestArch 5.1.0:** "generally inspired by ArchUnit". Rules are pytest tests with a fluent API (`Rule().modules_that().are_sub_modules_of(...).should_not().import_modules_that()...`) and a layer API, but it scans imports only, the same evidence import-linter uses. It is a small project (about 180 stars).
- **tach 0.35.3:** native `expose` interfaces, visibility rules and layers, and it is fast. It is pre-1.0, has no baseline (only `unchecked`, `exclude` and inline ignores), and the research advised against running it next to another enforcer.

**Decision: import-linter is the only import-graph enforcer.** PyTestArch is not shipped: every rule it can express, import-linter already expresses, and two engines over one graph would mean two policies, two baselines and two failure formats. tach is not shipped either, for the same reason, and because it has no ratchet.

**Decision: ship ArchUnit-style pytest tests for the rules import-linter cannot express.** They live in `tests/architecture/` as plain pytest. They use reflection, the AST and grimp (import-linter's graph library, so both read the same graph), and each one reads `architecture.toml`. They are the analog of the Next.js template's ArchUnitTS and resolved-graph tests:

| Rule | How it is checked |
| --- | --- |
| Every door `__all__` callable carries an `@operation` access policy | reflection over the door and the access registry |
| Every route has an auth dependency or is in the public allowlist | iterate `app.routes` and their dependants |
| A door exports only names defined in `service`, `schemas` or `errors`, never a repository, model or `DeclarativeBase` subclass | reflection, `__module__` of each export |
| Every table in `Base.metadata` belongs to the module the policy names | reflection over mapped classes |
| `schema.py` imports every `models.py` | grimp plus the file list |
| Every file in a module has a declared role (no unclassified files) | file list against the role table |
| `rules.py` calls no clock, randomness, env or file APIs (`datetime.now`, `random`, `uuid4`, `os`, `time`, `open`) | AST |
| No `await` of a client or `httpx` call inside `async with in_transaction()` | AST |
| Workflow docstrings carry the four-question header, and no two headers are identical | `ast.get_docstring` |
| A migration with `PHASE = "expand"` contains no drop, rename, `NOT NULL` tightening or type narrowing | AST over `alembic/versions/` |
| `.importlinter` matches what the generator would write | regenerate and compare |
| `.env.example` names match `Settings` fields exactly | reflection (section D) |

Every rule, contract and test gets a deliberate-violation fixture under `tests/fixtures/arch/<rule>/`, a clean twin, and an assertion on the exact contract name or message. Never-baselinable contracts (`system.py`, `jobs.py` and `router.py` protection, env reads outside `config/`, framework imports in `service`, `repository` or `rules`) are generated without `ignore_imports`, and the generator refuses baseline lines for them. A stated limit: import-linter baselines are per module pair, so a second violation of the same pair in the same file is invisible.

**C3. Makefile contract.** Conventional and self-documenting: `.DEFAULT_GOAL := help`, `SHELL := bash` with `.SHELLFLAGS := -eu -o pipefail -c`, `MAKEFLAGS += --warn-undefined-variables --no-builtin-rules`, every target `.PHONY`, and one `## description` comment per target, which `help` prints. Targets are thin wrappers over `uv run`, with no logic in make. Anything longer than a line is a script under `scripts/`. CI calls the same targets, so local runs and CI runs cannot drift.

| Target | Runs |
| --- | --- |
| `help` | lists targets and their descriptions (default) |
| `setup` | `uv sync --locked`, `prek install --hook-type pre-commit --hook-type pre-push` |
| `dev` | `uv run fastapi dev` (reload), fixture providers, local Postgres |
| `run-worker` | `uv run procrastinate --app=app.worker.app worker` |
| `format` | `ruff format`, `ruff check --fix` |
| `lint` | `ruff format --check`, `ruff check`, `deptry src`, vulture ratchet |
| `typecheck` | `mypy` (strict, from pyproject) |
| `test` | unit tests, no database, sockets disabled |
| `test-integration` | integration tests against real Postgres (testcontainers, or `TEST_DATABASE_URL` in CI) |
| `arch` | `lint-imports`, `pytest tests/architecture`, baseline shrink, diagram `--check` |
| `check` | everything CI runs: lint, typecheck, test, test-integration, arch, openapi drift, `alembic check`, secrets-scan |
| `migrate` | `alembic upgrade head` |
| `migration` | `alembic revision --autogenerate -m "$(name)"` |
| `openapi` | rewrite `openapi.json` from `app.openapi()` |
| `secrets-scan` | `gitleaks git` over the full history |
| `secret-set` | reads a value from a hidden prompt and pipes it to the configured secret store on stdin (section D) |
| `docker-build` | builds the `web`, `worker` and `migrate` targets |
| `clean` | removes caches and build output |

Two variables let a team inject secrets without editing targets: `RUN ?=` is a command prefix (`make dev RUN="op run --env-file=.env.op --"`), and `SECRET_STORE ?=` selects the backend for `secret-set`. GNU's standard targets name `check` as "perform self-tests", which is why the full gate is `check`.

**Follow-up for Next.js (recorded, not done here):** the Next.js blueprint gets the same Makefile contract with the same target names, wrapping its pnpm scripts, so every repo built from a blueprint has identical entry points for people, agents and CI. The target set is the one above, minus `run-worker` until 1.1.0's worker lands. Proposed for Next.js 1.2.0.

### D. Secrets: the standard

**Threat model.** A secret leaks through four paths: a file in the repo or its history; a file on disk that a person, a tool or an AI agent reads; process output (logs, argv in `ps` and shell history, agent transcripts); and an over-broad identity. The standard closes each path with one mechanism, and checks it where a tool can.

**The options compared (2026-11-07):**

- **(a) Encrypted files in the repo.** sops 3.13.3 (a CNCF Sandbox project) encrypts values in YAML, JSON and ENV and leaves the keys readable; its backends are age, PGP, AWS KMS, GCP KMS and Azure Key Vault, and with KMS, access is an IAM grant that can be revoked and is audited. git-crypt 0.8.0's README says it "does not support revoking access", has "no support for rotating the key", and does not encrypt file names or metadata. dotenvx 2.38.2 encrypts each `.env` value with a public key; the private key lives in `.env.keys` or `DOTENV_PRIVATE_KEY`. All three keep ciphertext in git history forever, so revoking a person means rotating every secret they could decrypt.
- **(b) A cloud secret manager as the source of truth, injected at runtime.** Google Secret Manager or AWS Secrets Manager hold the values. The platform injects them: Cloud Run mounts a secret as a file or resolves an env var at instance start, and the runtime identity needs `roles/secretmanager.secretAccessor` on that secret. Access is per secret, per identity, audited (data-access logs) and rotated by adding a version. Google's best-practices page says to reference pinned versions rather than `latest`, to bind IAM at the secret level, and to "avoid passing secrets ... through environment variables" (dependencies may log the environment), with an exception for serverless platforms.
- **(c) Developer tooling that injects at process start.** 1Password CLI `op run` resolves `op://vault/item/field` references from an env file into the child process only, masks values in output unless `--no-masking` is given, and uses scoped service accounts in CI. Doppler and Infisical do the same with their own stores. `gcloud secrets versions access` at process start needs no other vendor, but prints the value to stdout, so a script must capture it and never echo it.

**Recommendation (default):** (b) for every deployed environment, (c) for the rare local session that needs a real credential, and a template designed so local development needs no secrets at all.

1. **Local development needs no secrets.** Every third-party client has `fixture` and `noop` providers, and `fixture` is the default outside production. Local Postgres uses a throwaway password from `compose.yaml`, which is not a secret. A gitignored `.env` may hold non-secret local overrides only.
2. **When a developer needs a real credential locally**, it is injected at process start and never written to disk: `make dev RUN="op run --env-file=.env.op --"`. `.env.op` holds references only and may be committed in a private app repo; the template ships `.env.op.example`. Doppler (`doppler run --`) or Infisical (`infisical run --`) are equally acceptable when a team already uses one. The rule is the same either way: a reference on disk, the value only in the child process.
3. **Deployed environments** read from the secret manager through the platform. The template's settings read mounted files through pydantic-settings `secrets_dir` (default `/run/secrets`), with env vars as the fallback. The same code then works for Cloud Run volume mounts, Kubernetes secret volumes and Docker secrets, and it follows Google's advice to prefer files where possible. Deploy config pins secret versions. Rotation means: add a version, deploy a revision that references it, verify, then disable the old version, so rollback is a redeploy.
4. **Least privilege.** Each runtime identity (web, worker, migrate) gets `secretAccessor` on exactly the secrets it reads, bound at the secret level, and data-access audit logs are on. Humans and agents hold no standing accessor role on production secrets. Seeding and rotating go through `make secret-set NAME=...`: a hidden prompt (`read -rs`) pipes the value on stdin to `gcloud secrets versions add NAME --data-file=-`, or the AWS equivalent selected by `SECRET_STORE`. The value is never an argument.
5. **CI uses Workload Identity Federation, with no keys.** The template's CI needs no cloud identity, because tests use fixture providers and a Postgres service container. The deploy example in `docs/secrets.md` uses `google-github-actions/auth@v3` with `id-token: write` and a deployer identity that can deploy but cannot read secret values. The AWS variant uses GitHub OIDC with `aws-actions/configure-aws-credentials`.

**Settings loading** (`config/settings.py`): one pydantic-settings `BaseSettings` with `env_prefix="APP_"`, `env_nested_delimiter="__"`, `secrets_dir` and `extra="forbid"`. Every credential is `SecretStr`, so `repr` and logs show `**********`, and `.get_secret_value()` is called only inside the client that uses it. A `model_validator` fails closed in production when a required secret or public URL is missing. It is the only module allowed to read `os.environ` (TID251 plus an import-linter contract).

**`.env.example`** lists names only, one comment each: what it is, whether it is a secret, and where it comes from in each environment. An architecture test fails when it and `Settings` disagree.

**Keeping AI agents safe.** Each measure is shipped in the template and checked where possible:

- **There are no secret values in files an agent can read.** That follows from points 1 and 2: no plaintext `.env` with secrets, no `.env.keys`, no decrypted sops output in the tree.
- **The committed `.claude/settings.json` adds deny rules:** `Read(./.env)`, `Read(./.env.*)` with a `Read(!./.env.example)` carve-out, `Read(./.env.keys)`, `Read(**/*.pem)`, `Read(./secrets/**)`, and Bash denies for value-printing commands (`printenv`, `env`, `gcloud secrets versions access *`, `op read *`, `op item get *`, `sops -d *`, `sops decrypt *`). Claude Code's permissions page states the limit: Read deny rules also cover `cat`, `head`, `tail` and redirections, but not "arbitrary subprocesses that read ... files indirectly". So the same file enables the sandbox (`sandbox.enabled: true`, `sandbox.filesystem.denyRead` for those paths), which the docs describe as OS-level enforcement for shell commands and their children.
- **Agents run injected commands only through make targets.** `op run` masks values in output.
- **Secrets never go in argv.** Values travel on stdin, in mounted files or in the injected environment, never as flags: argv shows in `ps`, shell history, CI logs and agent transcripts. Lint catches hardcoded secrets (S105 to S107); `make secret-set` is the sanctioned path for values.
- **Logs are redacted.** A structlog processor masks keys matching `password|secret|token|api_key|authorization|cookie` and every `SecretStr`, and it is unit-tested with a planted value. The settings object is never logged whole. httpx clients drop auth headers from debug logs.
- **Secret scanning.** gitleaks 8.30.1 runs as a pre-commit hook on staged changes, and `make secrets-scan` (in `check` and CI) scans the full history. A test plants a fake key in a temporary repo and expects a failure.

**Verdict on encrypted files in repos.** Fine when a GitOps controller (Flux, Argo CD) decrypts at deploy time, or when a small team uses sops with a cloud KMS key: access is IAM, revocable and audited, the files hold rarely changing config, and no developer or agent machine holds a decryption key. Not fine with git-crypt (no revocation, no rotation); with age or PGP keys shared across a team (leaving means rotating everything); with dotenvx or any scheme whose private key sits in a file in the working tree (plaintext-equivalent to an agent); for credentials that rotate often; or where an audit trail per read is required. The template ships no encrypted files. `docs/secrets.md` documents the sops plus KMS setup as the GitOps option.

### E. Running it

`ARCHITECTURE.md` "Running it" and the template carry the research's production defaults:

- Build once and promote one image.
- The Dockerfile follows uv's Docker guide: a pinned uv image, `uv sync --locked --no-install-project --no-editable` as the dependency layer, `UV_COMPILE_BYTECODE=1`, `UV_NO_DEV=1`, a non-root `USER`. It has three targets: `web`, `worker` and `migrate`.
- One uvicorn process per container, `CMD` in exec form, `--proxy-headers` behind a TLS proxy, no gunicorn.
- `/healthz` (process only) and `/readyz` (database ping and migration head), both excluded from tracing and access logs.
- Migrations run as a job before the traffic shift, expand/contract only, gated by `alembic current --check-heads`.
- The Procrastinate worker runs in its own service (CPU always allocated, at least one instance), never in the web process.
- structlog JSON to stdout, carrying `request_id`, `trace_id` and `span_id`.
- OpenTelemetry, on only when an endpoint is configured.
- The worker joins to the data through an inbox row: the durable intent is a row, and a periodic task drains it.

## Open choices

These are still genuinely open; each has a recommendation.

1. **Secret scanner.** gitleaks 8.30.1 (recommended for 1.0.0) vs betterleaks. gitleaks is mature and its rules are widely known, but its README now says "feature complete ... security patches only", and its author has moved to betterleaks (v1.10.0, with v2 in development). Recommendation: ship gitleaks, and switch in a minor release once betterleaks v2 is stable and documents its pre-commit hook and config migration.
2. **Where the shared principles live.** Recommendation: copy the text into `fastapi/ARCHITECTURE.md` now, worded identically to Next.js 1.1.0. After both merge, a follow-up moves it into a root `PRINCIPLES.md` that both blueprints link to. The alternative, a root file in this PR, would edit the Next.js blueprint, which this plan must not do.
3. **One hook runner across stacks.** Recommendation: prek for Python now, and decide the cross-stack question together with the Next.js Makefile follow-up. lefthook would give one runner for both stacks, but it replaces husky and lint-staged in Next.js and adds a Go binary to Python repos. Identical `make` targets give most of the benefit without it.
4. **Committing an agent settings file in a neutral template.** Recommendation: ship `.claude/settings.json`, because the deny rules and the sandbox are the enforceable half of agent safety. Also ship an `AGENTS.md` that says the same in tool-neutral words, so other agents get the rules as text.

## Risks

- **Procrastinate's maintenance.** Its README asks for more maintainers, although 3.10.0 shipped in 2026-09. Mitigations: jobs sit behind each module's `jobs.py` door, so swapping in pgqueuer touches only the doors and `worker.py`. The spike in step 4 settles the transaction question early.
- **Baseline granularity.** import-linter baselines are per module pair, not per occurrence. This is documented as a limit and partly covered by the shrink check.
- **Agent safety has limits.** Deny rules do not cover a script that opens files itself, so the sandbox carries the OS-level part. A team that disables the sandbox loses it, and `docs/secrets.md` says so.
- **Env-var secrets leak through dependencies that log the environment.** The default is mounted files; env vars are the fallback only.
- **Tool churn.** ruff adds rules every minor release (the family list is explicit, so new rules arrive only through a deliberate change), ty is still 0.0.x, and prek is young (pre-commit stays the fallback).
- **make on Windows.** Windows has no native make. The docs name WSL or `uv run` with the commands in the target table.
- **Scope.** About 11 commits covering docs, a template, a policy generator, about 20 rules with fixtures, and the secrets tooling. Each step is a commit, so review can follow the order.
