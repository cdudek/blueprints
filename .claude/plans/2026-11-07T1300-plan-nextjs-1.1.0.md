# Next.js blueprint 1.1.0: principles, full default layout, field fixes

## Why

The owner chose the modular monolith with doors (option C in the architecture research of 2026-11-07) for its next app and asked for the blueprint to carry three things it doesn't carry today:

1. The concepts behind the rules, as general principles, so a reader knows why each rule exists.
2. A complete default repository layout, beyond `src/`: services, worker, migrate job, Dockerfile, tests, docs and infra.
3. The general rules learned from the first two adoptions (the first adopting app and the plan for the next one).

The first adopting app took 1.0.0 on 2026-11-06 and fixed 24 things in the machinery. The general ones come back here, so the next app doesn't fix them again.

Release type: minor (1.1.0). 1.0.0 policy files keep working, because every new policy key is optional and defaults to 1.0.0 behaviour. New rules may produce new findings, which the CHANGELOG's minor rule allows.

## Scope

### A. Concepts and principles (docs)

`ARCHITECTURE.md` gets a new section 2, "Principles", before the rulebook. Each principle gets one paragraph, its source, and the rules and folders that carry it out:

- Cut along decisions that are likely to change (Parnas).
- The top level shows the domain (screaming architecture).
- Dependencies point one way and never cycle.
- A module has a small public surface and keeps the rest private.
- Each module owns its data.
- Boundaries need a tool, adopted with a baseline that only shrinks.
- Parse at the edge, then trust the types.
- Pure core, side effects at the shell.
- Abstract only what really varies.
- Don't distribute early.
- Next.js specifics:
  - a server-only data layer
  - actions are public endpoints
  - no auth in layouts
  - no barrel files
  - one encryption key across instances

A short "where the sources disagree" note follows: layers vs slices, rich model vs transaction script, events vs direct calls. It explains which side the blueprint takes and why.

### B. Full default layout

**Repository root**, with a one-line job for each folder:

```text
.github/            CI, deploy
docs/               all prose; architecture.md carries the generated diagram
drizzle/            migrations
infra/              optional: infrastructure as code when it lives with the app (README says when not)
public/             static assets
quality/            baselines, renames, duplication exceptions
scripts/            ops scripts; arch/ and quality/ checks
services/<name>/    other runtimes, one folder each (README: Python with uv, flat src/ and tests/, own Dockerfile,
                    a JSON-schema contract the app's client tests against)
src/                the Next.js app
tests/              architecture/, e2e/ (moved from e2e/), integration/, tooling/, fixtures/, helpers/
Dockerfile          targets: web (standalone), worker, migrate
architecture.json   the policy
```

**Inside `src/`:**

- `instrumentation.ts`: a declared root, holding OpenTelemetry and `onRequestError`.
- `worker.ts`: a declared root. It is the entry point of the worker process, and calls `job` operations from a Postgres queue loop. The template ships it with the existing billing job, so a worker exists from the first commit.
- `app/_workflows/`: named cross-module workflows with the four-question header. Actions and routes call one workflow or one operation.
- `app/**/_shell` and `app/**/_components`: composition folders. They may import `ui/` and modules' browser doors only, and get their data as props.
- `shared/auth.ts`: holds only the session type, `requireUser(session)` and `requireRole(session, role)`. An auth library that persists to the database lives in a module (the template's stub moves to `modules/accounts`, as decided).
- Unit tests stay colocated (`*.test.ts` beside the code). The docs now say so.

**Production defaults** go in a new section 12, "Running it":

- Build once and promote.
- Share one `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` across instances, and pin `deploymentId`.
- Pass public values at runtime.
- Run migrations as a job before the traffic shift, expand/contract only.
- Use a Postgres queue in its own worker process, never in the web process on request-billed platforms.
- Health (`/api/health`) and readiness routes.
- Logs in JSON with the trace field.
- Kubernetes only when its cost is justified.

### C. Rules and tooling

Ported from the first adopting app (general items only; Biome and app-specific ones stay there):

- Policy `layout` block (optional): every hard-coded path is configurable, and the defaults are 1.0.0's paths.
- `arch:baseline:write`, plus `--write-baseline` for the knip and jscpd ratchets. Never-baselinable findings are refused.
- Baseline shrink:
  - A baseline absent at the merge base counts as "adopted".
  - An unparseable file or a git error fails closed.
  - `jscpd-exceptions.json` ratchets too.
- Verified renames: the source existed at the base and the destination didn't. A split (source kept) counts as a move.
- `applyRenames` rewrites whole path fields, not substrings.
- jscpd identities use repo-relative paths, so same-named files in different roots don't collide.
- Closures stop at `"use server"` files (they are reached, not entered).
- `server-only` must be the first statement of a server file.
- The diagram renders read exceptions from `file`, labels edges "uses a door", and guards its entry point with `pathToFileURL`.
- `declared-edges-acyclic` replaces the hard policy test, so a brownfield cycle can be baselined edge by edge.
- `modules-declared` reports a role selector that matches no file.
- Failure messages resolve to `file:line`.
- Policy-changes lists `baseline-renames.json` and `jscpd-exceptions.json`, uses a 256 MB buffer and never fails.
- CI: edits to the generated diagram, `quality/` and policy files are not docs-only.
- `roots` gains `instrumentation.ts`.

New in 1.1.0:

- `shared-no-clients`: `shared/` never imports `clients/`. (`shared-no-modules` already covers modules, db and app.)
- `roots-no-modules`: `proxy.ts` and `instrumentation.ts` import no module. `worker.ts` may import server doors.
- `composition-folders`: `_shell` and `_components` import `ui/` and browser doors only.
- `workflow-header`:
  - It covers `app/_workflows/**`.
  - It reads the header block rather than any five words anywhere.
  - No two workflows may carry identical headers.
- `system-operations-from-routes-only` also accepts `src/worker.ts` and `app/_workflows/**` called from a route or the worker.
- The default branch is read from `git symbolic-ref refs/remotes/origin/HEAD`, with `main` as the fallback. `BASELINE_BASE_REF` still overrides.

Every new or changed rule gets a violating fixture, a clean twin, an exact-message row and an ESLint `mustFail` row where ESLint can express it, as `fixtures.test.ts` and `eslint.test.ts` require.

Not taken from the first adopting app:

- Biome boundaries.
- The `test/` mirror layout.
- Central-tables mode.
- The door-exports relaxation.
- `leafModules`, `naming`, `fileSize` and `testDirs`. These go on the "add later" list, with the first adopting app named (without its name) as the first user.

   1. `e2e/` moves to `tests/e2e/`

   3. `src/worker.ts` with a Postgres queue loop around the billing job
   4. `src/instrumentation.ts`

   7. CI jobs: worker typecheck, Docker build smoke

6. Full check:
   - `pnpm check` in `nextjs/template` on Node 22, including E2E against a migrated local Postgres, and `BASELINE_BASE_REF=main pnpm arch:baseline`.
   - `new-module.test.ts` passes, with the generated module clean under every new rule.
7. One PR to `cdudek/blueprints` from `feat/nextjs-1.1.0`. The owner merges.

## Then the next app

The next app's target-architecture record moves from "the blueprint's 1.0.0 scripts plus the first adopter's fixes" to "blueprint 1.1.0". Its phase 0 starts once 1.1.0 is merged.

## Open choices (decided by the owner on 2026-11-07)

1. **Worker queue in the template:** graphile-worker. Decided: LISTEN/NOTIFY, cron and job keys with no extra infrastructure; pg-boss is not used.
2. **Auth in the template:** the stub moves into a `modules/accounts` example. Decided: `shared/auth.ts` keeps only the session type, `requireUser(session)` and `requireRole(session, role)`.
3. **Python example in `services/`:** a README only. Decided: no Python service or CI job in the template; the README may say that a Python blueprint will live next to the Next.js one.

## Risks

- **Scope:** about 25 machinery changes, 6 new rules, and a layout and docs rewrite. Each build step is its own commit, so review can follow the order.
- **Public repo:** nothing names the adopting apps, companies or people. Examples stay orders and billing.
- **Node:** the template needs Node 22. The default shell has Node 20, so every command runs under `nvm use 22`.
