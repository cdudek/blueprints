# Internationalisation

Every user-facing string is a message key from the first commit, even with one locale. Adding a language later is then a content task, not a refactor. The URL decides the locale; the server formats everything in one fixed timezone.

## Rules

### Strings

- **I18N-1: No literal user-facing text in components, actions, emails or errors.** Every string is a key in a message catalog. This includes aria-labels, alt text, validation messages, page titles and email subjects.
- **I18N-2: Use next-intl,** latest stable at build time, with one catalog folder per locale and one file per namespace (for example `messages/en/billing.json`). A new locale is a sibling folder.
- **I18N-3: Namespaces are typed.** Keys are checked at compile time against the default-locale catalog; a missing or misspelled key fails typecheck.
- **I18N-4: Keys name the place and the meaning,** not the words (`billing.invoice.empty.title`). Never build a key by string concatenation. Never concatenate translated fragments into a sentence; use ICU placeholders and plural rules.
- **I18N-5: Content authored at runtime** (CMS entries, user text) is separate from interface strings and is stored per locale in its own tables or fields.
- **I18N-6: Copy language equals the locale config.** If a surface is intentionally one language only (for example admin), list the exception in one place.

### Routing

- **I18N-7: The URL decides the locale.** Prefix policy is chosen once per product and recorded as a decision: default locale without prefix and all others prefixed, or every locale prefixed. With the unprefixed policy, the prefixed duplicate of the default locale redirects (301). Never decide locale from IP; the Accept-Language header only suggests a first redirect, and the choice is remembered.
- **I18N-8: Machine routes sit outside locale routing:** `/api`, `/mcp`, `/oauth`, `/.well-known`, `/healthz`, `/readyz`, sitemap, robots, `llms.txt`.
- **I18N-9: Links are built by one path helper** that adds the locale. The same helper feeds canonical, hreflang and sitemap (see [seo](seo.md)).
- **I18N-10: `html lang` is set from the locale.** `og:locale` and schema `inLanguage` are derived from it, never hardcoded.

### Formatting

- **I18N-11: Dates, numbers, currency, lists and relative time use the platform Intl APIs through next-intl formatters,** never hand-built strings. Currency is always shown with its ISO 4217 code or the locale format of it, and stored as DAT-3 in [data-and-migrations](data-and-migrations.md) defines, with the currency code.
- **I18N-12: One fixed server timezone** (set per product, usually UTC for storage and one named zone for display). Server-rendered dates use it so server and client output match. User-local display, if needed, happens in a client component after hydration.
- **I18N-13: Emails and exports** use the recipient's stored locale, not the request locale.

### Terminology

- **I18N-14: A glossary per locale** lists the product nouns and verbs and the one translation for each. One word per meaning. A test fails when a forbidden synonym appears in a catalog (see [copy](copy.md)).
- **I18N-15: Brand and product names are not translated.**

## How to apply

1. Create the default-locale catalog and the typed namespace setup before the first component.
2. Add the path helper and locale middleware; exempt machine routes.
3. Choose the prefix policy, default locale, fixed timezone; write them in a decision record (see [decisions](decisions.md)).
4. Write the glossary for the default locale before writing copy.
5. To add a locale: copy the catalog folder, translate with the glossary, add the locale to config, sitemap, hreflang and the language switcher, and run the key-parity check. Ship it only when every namespace is complete or the fallback is explicitly allowed.
6. When changing a string, change the key's text, not its meaning; if the meaning changes, add a new key and delete the old one.

```
messages/
  en/  common.json  billing.json  emails.json
  de/  common.json  billing.json  emails.json
src/i18n/   config, request setup, path helper, typed keys
```

## Checks

- Typecheck fails on unknown keys.
- Key-parity test: every locale has exactly the keys of the default locale, except namespaces with an explicitly approved fallback; placeholders and plural forms match.
- Lint or test fails on literal user-facing strings in components (JSX text, `aria-label`, `alt`, `title`).
- Glossary test for forbidden synonyms per locale.
- Test that machine routes are not prefixed and prefixed duplicates redirect.
- Left to review: translation quality, tone, cultural fit.

## Mistakes to avoid

- "We only have one language" led to literal strings everywhere, and a costly retrofit.
- Locale config listed a language the copy did not ship; users saw mixed languages.
- Concatenated fragments broke grammar in other languages.
- Server and client formatted dates in different timezones and hydration mismatched.
- `og:locale` hardcoded to the default locale on translated pages.
- Locale middleware caught `/mcp` and health routes and broke clients and probes.
- Translating runtime content with interface catalogs, or the reverse.
